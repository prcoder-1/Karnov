# Декомпиляция KARNOV.EXE и восстановление алгоритмов

Метод, инструменты и накопленные факты. Документ описывает **как** велась
работа (чтобы её можно было продолжить или повторить на другой игре) и
**что** в итоге выяснено про устройство Karnov.

Смежное: `KARNOV.md` — устройство игры и форматы файлов;
`docs/DECOMPILE_NOTES.md` — таблица «адрес → имя функции»;
`AUDIO.md` — звуковая подсистема.

---

## 1. Исходные данные и адресация

| Параметр | Значение |
|---|---|
| Формат | MS-DOS MZ, Borland Turbo-C 1987, compact model |
| Заголовок | 0x1800 байт; точка входа = `file 0x1800` |
| DS | `0x1D99`; DS-сегмент в файле с `0x1F190` |

Две системы координат в адресах, обе нужны:

* `cs:SEG:OFF` — как адресует сам код (far-вызовы);
* `file 0xXXXXX` — смещение в EXE, для дизассемблера.

Перевод: `file = 0x1800 + SEG*16 + OFF`, `DS:0xNNN = file 0x1F190 + 0xNNN`.

Compact model означает **много мелких кодовых сегментов** (по одному на
модуль) и один общий DS. Практическое следствие: вызов внутри модуля —
ближний (`E8 rel16`), между модулями — дальний (`9A off seg`). Поиск
«кто вызывает эту функцию» по far-указателю находит только межмодульные
вызовы; внутримодульные приходится искать сканом `E8` с проверкой цели
(так был найден драйвер sky-цепи).

## 2. Инструменты

### 2.1 `karnov_c/tools/decompile_ai.py`

Главный инструмент. `python3 tools/decompile_ai.py <тип|SEG:OFF> [размер]`:

* находит обработчик по таблице `DS:0x10FE` (58 × far-указатель);
* линейно дизассемблирует его (`ndisasm -b 16`);
* **раскрывает jump-таблицы**: находит `jmp [cs:bx+X]`, берёт длину из
  предшествующего `cmp ax,N`, печатает цели и исключает байты таблицы из
  потока кода (иначе ndisasm разбирает их как инструкции и весь листинг
  «съезжает»);
* подписывает известные хелперы и поля `ActiveObject` прямо в листинге.

Без раскрытия таблиц разбор одного типа занимал часы; с ним — минуты.

### 2.2 Прочее

* `ndisasm -b 16 -o <origin>` + `dd` — точечные дампы.
* `tools/spawn_oracle.py` — независимая реализация алгоритма спауна на
  Python, сверяется с логом порта (`KARNOV_SPAWN_LOG`).
* `tools/extract_anim_tables.py` — генерация таблиц анимаций в C.
* Точечные python-сканы по бинарнику (см. §5) — для «кто пишет это поле»,
  «где начисляются очки» и подобных вопросов.

### 2.3 Отладочные хуки порта

| Переменная | Что делает |
|---|---|
| `KARNOV_DBG_TYPE=<n>` | трассировка объектов типа: x/y/hp/вспышка/подфазы рядом с координатами игрока |
| `KARNOV_DBG_SPAWN=1` | печать каждого спауна с позицией и HP |
| `KARNOV_SPAWN_LOG=<файл>` | машинный лог для оракула |
| `KARNOV_DBG_OBJECTS=<N>` | раз в N кадров — статистика пула объектов |
| `KARNOV_START_X=<px>` | стартовая позиция Карнова (подвести к нужному врагу) |
| `KARNOV_DBG_INPUT=<hex>` | подмешать биты ввода (01 вправо, 04 сидя, 10 огонь) |
| `KARNOV_DBG_GIVE=<id,…>` | выдать предметы |
| `KARNOV_DBG_KILLBOSS=1` | убить goal-объект сразу после спауна |
| `KARNOV_DBG_DEATH=1` | трассировка гибели: причина, аним-состояние, кадр, якорь, vy, «музыка доиграла» |
| `KARNOV_DBG_AUDIO=1` | трассировка вызовов музыки и SFX (работает и с `--no-audio`) |

## 3. Скелет обработчика: что искать в листинге

Все 58 AI-обработчиков устроены одинаково, и распознавание этого шаблона —
90% работы:

```
handler():
    ax = [0xD8A2]                  ; state_byte объекта
    if (ax > 6) return
    switch (ax) → jmp [cs:bx+TBL]  ; ТАБЛИЦА СОСТОЯНИЙ
        0,1 = INIT   2 = THINK   4 = «получил урон»   6 = удаление
THINK:
    ++[+0xEB]                      ; счётчик тиков подфазы
    si = [+0xE9]; [+0xE9] |= 1     ; подфаза; чётная = одноразовый вход
    if (!(si & 1)) [+0xEB] = 0
    switch (si) → jmp [cs:bx+TBL2] ; ТАБЛИЦА ПОДФАЗ
```

Идиома `si = misc; misc |= 1` встречается почти везде: чётная подфаза
выполняет «вход» (задать скорости, кадр, флаги) ровно один раз, дальше
работает нечётная — «продолжение». В порту это переносится как
`case N: …; /* fallthrough */ case N+1: …`.

Возвращаемое значение — биты в `[0xD963]` (`ai_result`):
1 = удалить объект, 2 = сменить аним-состояние (номер в `[0xD88C]`),
4 = применить текущий кадр, 8 = передать управление другому объекту,
0x10 = отдать объект обработчику гравитации/пуфа.

## 4. Ключевые поля ActiveObject (245 байт, `DS:0x2824`)

| Смещение | Что | Замечание |
|---|---|---|
| +0x08 / +0x0C | x_world / y_world | **левый край / ВЕРХ** спрайта; X в 2px-единицах |
| +0x0E…+0x1D | vx, vy, ax, ay | Q16.16, интегрируются каждый кадр (UPDATELOCS) |
| +0x1E | num_bboxes | 0 = не рисуется |
| +0x20… | bbox[8] по 18 байт | sprite, dx, dy, x0, y0, x1, y1, **flag**, was_visible |
| +0x2E | box0.flag | **коллизия включена**, а не видимость |
| +0xB6 | state_byte | 0..6 |
| +0xC5 / +0xC9 | frame_idx / tick_period | троттлинг |
| +0xC7 | frame_ctr | тикает каждый кадр |
| +0xDD / +0xDF | «задели» / индекс партнёра | пишет pair-loop, НЕ родитель |
| +0xE1 / +0xE3 | номера пересёкшихся боксов | |
| +0xE5 / +0xE7 | obj_type / hit_points | obj_type: 0 игрок, 1 враг, 3 снаряд, 5 предмет, 9 декор |
| +0xE9 / +0xEB / +0xED / +0xEF | приватные поля обработчика | подфаза, счётчик, флаги |
| +0xF1/+0xF3 | parent_ptr | настоящий родитель (ставит spawn_child) |

Отдельно: позиция игрока для AI кэшируется в `[DS:0xD8BC]` (x_world) и
`[DS:0xD8BE]` (y_world). Сравнивать координаты врагов надо **с ними**, а
не с «центром/подошвой» — иначе всё прицеливание по Y уезжает на высоту
спрайта.

## 5. Приёмы, которые сработали

**Поиск по шаблону инструкции.** Вопрос «кто пишет поле +0xDF» решается
regex-ом по байтам (`26 89 87 DF 00` = `mov [es:bx+0xDF],ax`). Так
выяснилось, что +0xDF — это индекс задевшего объекта, а не родитель, и
рухнула целая цепочка неверных выводов.

**Привязка адреса к типу.** Для «кому принадлежит этот кусок кода» —
таблица обработчиков + правило «владелец = обработчик с наибольшим
адресом, не превышающим искомый, в том же сегменте». Так была построена
таблица очков: скан всех вызовов `add_score` + привязка к владельцу.

**Сканирование ближних вызовов.** `E8 rel16` с вычислением цели по всему
сегменту — единственный способ найти вызывающую сторону внутримодульной
функции (так найден драйвер sky-цепи `cs:0xFFA:0x163D`).

**Проверка гипотезы данными.** Прежде чем реализовывать «спаунер», стоит
посмотреть на записи уровней: у типа 8 во всех девяти уровнях
`range = (0,0)`, а условие спауна строгое — значит по триггеру он не
рождается никогда, и его создаёт код.

**Отрисовка спрайтов.** Многие вопросы («это орлы или лёд?», «в какую
сторону смотрит враг?») решаются за минуту, если выгрузить кадры из кэша
в PNG. Так выяснилось, что sky-цепь роняет льдинки, а не птиц, и что арт
врагов нарисован мордой ВЛЕВО.

## 6. Ошибки, которых стоит избегать

Все они реально были допущены в этом проекте:

* **Верить мануалу больше, чем коду.** «Первый удар — Карнов синеет,
  второй — смерть» из мануала не подтверждается: в коде у игрока 5 HP и
  симметричный обмен уроном, то есть касание почти всегда смертельно.
* **Считать `die_puff` смертью.** Это вспышка с ВОЗВРАТОМ исходного
  обработчика; удаление — отдельное состояние 6.
* **Путать `+0xDF` с родителем.** См. §5.
* **Отражать спрайты при развороте.** Движок арт не зеркалит: оба
  разворота лежат отдельными спрайтами, направление — это номер
  аним-состояния (state 0 = влево, 1 = вправо).
* **Реализовывать «по смыслу», когда листинг под рукой.** Каждый такой
  случай (тип 47 «прыгун» вместо турели, тип 22 «патруль» вместо
  статичного стража, тип 10 «преследователь» вместо маятника) потом
  всплывал как несоответствие.
* **Грепать вывод сборки по `error|warning`** при локализованном gcc:
  «Ошибка» мимо фильтра, и тесты идут со старым бинарником. Собирать
  через `LC_ALL=C make`.

## 7. Цикл проверки

1. Собрать: `LC_ALL=C make -j8` (предупреждений быть не должно).
2. Поведение типа: `KARNOV_DBG_TYPE=<n>` + `KARNOV_START_X` рядом с его
   записью в уровне (координаты — из `spawn_oracle.load_records`).
3. Спаун-регрессия: `KARNOV_SPAWN_LOG` + `tools/spawn_oracle.py`.
   **Оракул валиден только для прогонов без смертей игрока** — после
   гибели движок перевзводит записи rearm-циклом, чего оракул не знает.
4. Смоук: все уровни по 700 кадров, отдельно CGA.
5. Визуально: `--ppm` + PIL для увеличения кадра.

## 8. Что восстановлено (сводка)

* **Все 54 типа**, встречающиеся в данных уровней, — по листингу.
  Заглушки остались у 41 (в данных нет), 56 (секвенция конца уровня
  реализована в `game.c`) и 57 (декорация).
* **Дети и вспомогательные объекты**: шары «золотого человека», сегменты
  ловушки, снаряды врагов, выпадающее сокровище.
* **Боевая система**: сбор пар по боксам, обмен уроном (5 HP у игрока),
  вспышка при ранении и гибели, превращение в декорацию, неуязвимость по
  фазам у боссов.
* **Свиток конца уровня** — это тип 7 из данных уровня, а не
  синтезируемый объект: он взводится гибелью goal-объекта и появляется,
  когда игрок подходит ближе 0x50.
* **Sky-цепь**: связный список объектов типа 8 (падающий лёд), спаун
  1–2 штук раз в 390 кадров, «убийство цепи» проходом по списку.
* **Очки**: 8-разрядный BCD в `DS:0xD930`; константы в обработчиках тоже
  BCD (0x2600 = 2600). Таблица — `SCORE_BCD` в `src/ai.c`.
* **Гибель Карнова** (`0xE62:0x1791`, см. KARNOV.md §5.5): два входа —
  вода (`play_sound(7)`, player_state 7) и враг (`play_sound(2)` из
  pair-loop, player_state 6); падение с ay = 0.5, посадка по нижней
  кромке спрайта, трёхкадровое оседание #115→#117 при tick_period 8 и
  респавн по «музыка смерти доиграла И анимация в финальном состоянии».

## 9. Что осталось

* Каркас автомата состояний 4/5/6 с передачей управления через бит 8
  `ai_result`. Всё, что он обслуживает, работает через эквиваленты по
  видимому эффекту; каркас нужен только для покадрового совпадения.
* Вызывающая сторона некоторых редких механик (кто и с каким N зовёт
  sky-спаунер известно; кто создаёт объекты типа 41 — нет).
* Промежуточный кадр `#1` у выпадающего сокровища (тип 22) — опущен,
  так как механика падения в порту общая.
